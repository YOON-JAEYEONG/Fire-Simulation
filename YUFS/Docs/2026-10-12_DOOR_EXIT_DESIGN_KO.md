### 2026-10-13 구현 범위와 미완료 사항

- `YUFSExitTraversalComponent`: 안→밖 문턱 통과, 캡슐 전체 이격, 벽/문 충돌과 외부 바닥 확인 후 한 번만 결과 확정. 위치 복구 및 재생 이동은 통과 표본에서 제외.
- NPC·컨트롤러·타임라인·시험 집계가 명시적 탈출 결과를 사용한다. 성공한 NPC와 가방은 유지되며 실외 목표까지 이동한다. 실외 이동이 8초 이상 막히면 현재 위치에서 보이는 상태로 대기하고 경고를 남긴다. 이는 집결지 도착 성공이 아니다.
- 외부 경로/모션 담당에는 `ExteriorDispersal` / Walk 또는 Idle 지시를 발행한다. 외부 드라이버가 새 목적 유형을 처리하도록 팀의 어댑터 연결이 필요하다.
- 문은 발견/예약 범위와 조작 근접 범위를 분리했다. 지정된 여닫이 방향을 유지하고, 미닫이 이동량/여닫이 각도에서 통행 여유 폭을 계산한다. 기존 문 형식 자체는 변경하지 않았다.
- 전용 손잡이 애니메이션·IK는 미구현이다. 현재 근접·방향 확인 후 잠깐 정지하는 대체 처리이며, 이를 실제 손 접촉으로 주장하지 않는다. 이전 태블릿 동작을 문 열기로 재생하던 처리는 제거했다.
- Main 중앙 출구: 기존 모델 개구부 x=2070..2240, y=0에 폭170cm 포털을 맞췄다. 외부에 시험용 보행 바닥을 추가하고 내비게이션 범위를 확장했다. 바닥은 현장 측량 자료가 아니라 구현 검증용이다.
- 양끝 출구: 아래 추가 작업에서 별도 복사 벽 메시의 물리 개구부와 외부 바닥을 연결하여 활성화했다. 폭180×높이220cm는 작업 가정값이며 실제 건물 사양 확인이 필요하다.
- 외부 목표는 StableNpcId 기반 25개 격자 후보에 분산한다. 25명 초과나 ID 나머지 충돌 시 같은 후보를 공유할 수 있다. 대기 공간 예약/인원에 따른 확장까지 구현한 것은 아니다.
- 기존 위험 임계값·방송·인격·FDS 데이터는 수정하지 않았다. 기존 맵의 FDS 정렬 미검증/기본 파일 누락 경고는 별도 문제로 남는다.

## 1. 결론과 범위

문은 **통행을 제어하는 실제 물체**, 출구는 **실내에서 실외로 나간 사실을 판정하는 건물 경계**로 구분한다. 방문을 여는 것, 복도로 나오는 것, 건물을 탈출하는 것은 서로 다른 사건이다.

권장 목표는 다음과 같다.

> 같은 NPC가 실제 문의 조작부에 접근해 열고, 충돌 가능한 문틀 사이를 지나, 건물 밖으로 완전히 나간 뒤에도 보이는 상태로 이동한다. 집계와 되감기는 그 실제 이동 사건을 사용한다.

- 유지: 사용자 확인 출구 3곳(1층 양끝·중앙), JJW의 개인별 판단·위험 지각, 기존 경로 요청 관리, 가방 회수 중의 역방향 이동, 자유시점 관찰.
- 개선 범위: 문과 출구의 물리/시각/경로 연결, 조작 모션, 통과·대피 결과, 병목 및 재생의 일관성.
- 비목표: 모든 NPC의 100% 탈출 보장, 모든 대기 제거, 확률·위험 임계값 임의 조정, 방송 자동 추가, 새 소화 기능, FDS 유체 재계산.

## 3. 물리 배치: 디지털 트윈을 기준으로

### 실제 출구 3곳

서쪽·중앙·동쪽이라는 기존 식별과 대략적인 위치는 유지한다. 실내 벽 앞에 점을 두는 방식 대신 각 출구에 다음 요소가 일치해야 한다.

- 렌더링 메시와 충돌 메시 모두에 실제 개구부가 있음.
- 문턱 양쪽에 NPC가 설 수 있는 바닥이 있고, 실외 쪽까지 유효한 이동 경로가 이어짐.
- 문틀 폭·높이·문 종류·바깥 방향이 도면 또는 현장 자료와 맞음.
- 출구 표시와 문짝을 중복 배치하지 않음. 표시용 닫힌 문짝 위에 또 실제 문짝을 겹치지 않음.

2층 방문·계단실 문은 중간 통과 지점이다. 2층 NPC가 계단을 통해 1층 출구를 고르는 것은 정상이며, 출구 선택 전체에 ‘같은 층만’ 필터를 적용하면 안 된다. 층/높이 검증은 마지막 문턱을 실제로 통과할 때 한다.

### 실제 형상 수정과 임시 추상화의 선택

권장은 실제 개구부와 실외 동선을 만드는 방법이다. 메시 수정 및 팀원의 맵 작업 조율 비용이 들지만, 문 통과·병목·시각 확인을 같은 사실로 묶을 수 있다.

형상 수정 전에는 양끝을 **미구현 출구**로 명확히 표시한다. 별도 추상 실험에서 도착을 종료 조건으로 쓸 수는 있지만 이름을 ‘출구 지점 도착’으로 구분하고, 물리 탈출 시간·성공률과 합치지 않는다. 실제 출구가 3곳인 건물을 임시로 1곳만 활성화해 돌린 결과도 완성된 IT관 대피 결과로 해석하지 않는다.

### 문 형식

각 문을 미닫이/밀기/당기기/자동문으로 명시한다. 미닫이는 실제 해당 문일 때만 적용한다. 여닫이는 고정 경첩·허용 개방 방향을 사용하고, 최초 NPC가 어느 쪽에 섰는지에 따라 임의의 반대 방향으로 열리지 않도록 한다. 현실의 문짝이 공간을 차지하는 현상은 모델에 남겨야 한다.

## 4. 문 상호작용: 빨리 발견하고 실제 접촉에서 조작

```text
기존 목적지로 이동
  → 경로에 있는 문 발견·통과 계획
  → 조작 위치 접근 / 이미 열려 있으면 통과
  → 조작자 예약 + 손잡이/패닉바 접근 자세
  → 손 접촉 확인 → 문짝 이동
  → 몸이 통과할 여유 폭 확보 → 통과
  → 문 너머 여유 공간 도달 → 기존 대피/가방 경로 계속
```

- **발견 거리와 조작 거리를 분리한다.** 멀리서 발견해 속도·위치·사용할 손을 준비하되, 수동문은 실제 접촉 전에 열리지 않는다.
- **문 종류에 맞춰 움직인다.** 밀기/미닫이는 접근과 상체 동작을 겹칠 수 있다. 당기기는 문짝의 회전 공간을 비켜 짧게 재배치해야 한다. 모든 문에서 정지 시간을 0으로 만드는 것은 목표가 아니다.
- **통과는 개방 완료율이 아니라 공간으로 판정한다.** NPC 캡슐과 실제 반영하기로 한 휴대품의 폭, 문짝 위치, 문틀 사이 여유를 확인한다. 아직 못 지나갈 폭이면 기다리고, 충분한 폭이면 불필요하게 100% 개방까지 기다리지 않는다.
- **예약을 나눈다.** 조작자는 한 명, 통과 대기자는 별도다. 이미 열고 있는 문에 모두가 조작 예약을 시도하거나 양쪽에서 서로 밀지 않는다. 반대 방향의 가방 회수 NPC도 실제 통과 요청으로 처리한다.
- **열린 문짝은 계속 장애물이다.** 몸이 문짝을 뚫거나 문을 지워서 흐름을 맞추지 않는다. 자동 닫힘은 실제 문 사양으로만 켜며 통행 중인 NPC를 관통하지 않는다.
- **실패도 동작이다.** 잠김/물리적 막힘/예약 상실/위험 상승/취소를 구분해 현재 경로 담당에 알린다. 뒤로 비키기·대기·재탐색은 이유 있는 상태로 기록하고, 무제한 재요청 또는 순간이동으로 성공 처리하지 않는다.

새 전용 모션에는 손 접촉/손 놓기 시점을 표시하고 손 IK 목표를 문 객체에서 받도록 제안한다. UE의 Animation Notify는 애니메이션 시점에 맞춘 이벤트를 지원한다. 다만 Notify 자체를 물리 판정의 유일한 근거로 삼지 않는다. 요청 세대·예약·거리·가림을 실행기가 재확인하고, 누락/중복/취소 시에도 정체 없이 실패 처리한다. [UE 5.7 Animation Notifies](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-notifies-in-unreal-engine?application_version=5.7)

현재 네이티브 재생은 single-node 방식이다. 상체 문 동작과 하체 보행을 섞으려면 모션 담당의 AnimBP/몽타주 구성을 포함한 작업이 필요하며, 단순히 C++에 함수 하나를 추가해 손잡이 잡기까지 끝나는 것은 아니다. RL/Manny 스켈레톤 호환성 보호와 기존 외부 모션 담당 설정을 유지한다.

## 5. 출구 판정: ‘가까움’ 대신 실제 통과 사건

출구에는 공통 기준 좌표계를 둔다. 문틀 중심·바닥·폭·높이·바깥 방향, 실내 접근 구역, 실외 이격 구역, 연결 문(있다면)을 함께 정의한다. 장식의 회전·높이 보정을 성공 판정 좌표로 재사용하지 않는다.

권장 건물 탈출 조건:

1. 아직 대피 완료하지 않은 NPC가 실내에서 해당 출구에 접근했다.
2. 프레임 간 실제 이동 궤적이 문틀의 유효 개구부를 안→밖으로 통과했다.
3. 연결 문과 벽의 충돌을 우회하지 않았고, 문턱의 높이/실제 바닥이 맞다.
4. NPC 몸 전체가 외벽 밖으로 빠져나와 출입구를 막지 않을 여유 영역에 도달했다.
5. 동일한 실행/NPC에 대해 하나의 `BuildingExited` 결과만 발행한다.

단순 Overlap 한 번, 문 앞 150cm 접근, 바깥에서 시작한 NPC, 벽 너머 인접, 되감기·복구 순간이동은 탈출 사건이 아니다. 저프레임에서 영역을 한 번에 지나가는 경우에도 연속 이동 구간을 검사해야 한다.

### 밖으로 나간 뒤에도 같은 NPC를 보여 준다

`BuildingExited → 실외 분산 이동 → 외부 대기`를 표현한다. 건물 탈출 시각은 바꾸지 않되, 결과 확정으로 보행까지 즉시 정지시키지 않는다. 시뮬레이션의 마지막 NPC가 나왔을 때도 필요한 실외 표시 구간은 관찰 가능해야 한다.

‘건물 밖 이탈’과 ‘집결지 도착’은 별도 지표다. 실외 영역이 실제로 안전하다는 검증 없이 후자를 ‘안전 확보 완료’라고 표시하지 않는다. NPC를 성능상 비활성화할 필요가 있다면 문 앞이 아닌 실외 대기 이후에 처리하고, 기본 관찰 모드에서는 유지한다.

컨트롤러 집계, NPC/학습 종료, 타임라인은 같은 결과를 소비한다. `RunId, NpcId, ExitId, CrossingTime, ExteriorClearTime, Outcome` 같은 명시적 결과를 사용하고, 가시성으로 대피 여부를 추정하지 않는다. 재진입 허용 여부와 재집계는 이번 변경에서 새로 만들지 않고 기존 시나리오 범위로 제한한다.

## 6. 팀별 책임과 경로 연결

| 담당 | 책임 | 다른 담당을 침범하지 않는 조건 |
|---|---|---|
| 행동/JJW | 관측·기억·위험에 따른 대피/회수/도움 의도 | 문 앞에 왔다고 새 대피 결심을 강제하지 않음 |
| 경로 탐색 | 접근·통과·실외 목표, 비용·혼잡·실패 후 재탐색 | 문을 열거나 애니메이션/집계를 직접 완료하지 않음 |
| 상호작용 | 문 조작 가능 조건, 예약·진행·실패, 통행 여유 | 독자적인 위치 이동·출구 선택·위험 임계값 변경 금지 |
| 모션 | 문 종류/손/방향에 맞는 동작과 접촉 신호 | 애니메이션 완료가 곧 문 통과나 대피 성공은 아님 |
| 맵/모델링 | 실제 개구부, 바닥·계단·문 사양, 외부 공간 | 표시용 출구를 물리 출구로 간주하지 않음 |
| 결과/재생 | 단일 탈출 사건, 명시적 가시성·상태·문 포즈 기록 | 숨김 상태로 결과를 역추정하지 않음 |

문 개구부는 경로상의 ‘조건부 통행 구간’으로 연결한다. 열 수 있는 닫힌 문은 조작 비용을 가진 경로 후보이고, 사용 불가가 확인된 문은 우회 대상으로 기록한다. NPC가 보지 않은 잠금·위험을 모든 NPC에게 자동 공유하지 않는다.

Unreal의 Smart Link는 NavMesh 구간 연결과 동적 상태 표현의 후보가 될 수 있다. 다만 현재 JJW는 자체 비동기 경로와 웨이포인트 이동을 사용하므로 기존 이동을 그대로 둔 채 엔진의 링크 도달 콜백이 자동 동작한다고 가정하지 않는다. 기존 실행기와 연결하는 한 가지 이동 소유권이 필요하다. 연결만 추가해 벽이나 문짝 충돌을 통과할 수 있게 되는 것도 아니다. [Epic ANavLinkProxy 문서](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/AIModule/ANavLinkProxy?lang=en-US)

## 7. 화재·방송·정체와 분리해야 할 것

- 문 동작 개선을 검증하면서 방송 시각·연기 위험 임계값·가방 비율을 동시에 바꾸지 않는다. 기존 기록의 ‘20/20’은 실험 조건이 함께 바뀐 결과다.
- ‘문을 열기 위한 잠깐의 정지’, ‘줄을 서는 대기’, ‘화재 판단 전 지연’, ‘경로 불능’, ‘시뮬레이션 종료’는 서로 다른 상태다. 모두 버그성 정지로 묶지 않는다.
- 현재 소스에는 장기 정체 시 위치를 옮기는 복구가 있다. 실제 통행 검증에서는 발생 여부를 기록하고 해당 순간이동을 출구 통과로 인정하지 않는다. 표준 동작의 순간이동 제거/변경은 별도 승인할 행동 변경이다.
- 계단 추락은 문 개방 속도로 해결할 수 없다. 실제 계단 형상·충돌·NavMesh의 NPC 크기·낮은 프레임에서의 이동을 따로 검증한다.
- 기록된 FDS/VDB는 문을 열어도 재계산되지 않는다. 새 방문·벽의 개폐가 연기 유동까지 바꾼다고 주장하지 않는다. 원래 FDS의 문/벽/개구부 조건과 게임 배치가 다르면 물리적 재현의 한계로 기록한다.
- 관찰용 연기 투명도와 NPC가 읽는 위험 데이터는 별도 설정이다. 사람이 잘 보이게 하는 렌더링 변경으로 감지 위험이 바뀌어서는 안 된다.

## 8. 인수 기준

자동 검사와 실제 자유시점 렌더링 확인을 함께 사용한다. 이번 검토에서는 이 검사를 새로 실행하지 않았다.

| 상황 | 반드시 관찰·검증할 결과 |
|---|---|
| 단독 NPC와 닫힌 문 | 실제 접촉 전에는 수동문이 움직이지 않고, 조작 후 같은 NPC가 통과 |
| 열린 문/복도 옆의 무관한 방문 | 불필요한 조작·예약·정지 없이 경로 계속 |
| 2층 방→계단→1층 출구 | 방문은 탈출로 집계하지 않고 실제 1층 외부 통과만 집계 |
| 미닫이/밀기/당기기 | 실제 사양 방향대로 움직이며 형식별 유효 통과 폭을 검사 |
| 여러 NPC·역방향 가방 회수 | 한 조작자, 충돌 없는 통행 순서, 무한 예약 대기 없음 |
| 벽 앞 출구 표시/닫힌 문/잘못된 높이 | 가까워도 성공하지 않음 |
| 밖에서 생성/역방향 진입/반복 이벤트 | 가짜 성공·중복 집계 없음 |
| 정상 외부 이탈 | 몸 전체가 밖으로 나온 뒤 1회 집계, 화면에서 계속 보임 |
| 잠김·폐색·NPC 삭제·취소 | 예약 정리와 이유 있는 대기/경로 실패, 순간이동 성공 없음 |
| 일시정지·Stop/Start·되감기 | 문 포즈·NPC 통과·가방·결과가 일치, 이전 실행 예약 잔류 없음 |
| 저프레임·서버/화면 없는 실행 | 통과 누락/벽 관통/애니메이션 이벤트 누락에 의한 무한 대기 없음 |

성능·행동 비교는 같은 NPC 배치, 난수 시드, 화재 데이터/시간축, 방송, 가방 설정으로 반복한다. 문 조작 시간, 통과 대기 시간, 실제 충돌 정체 시간, 최초/최종 실외 이탈 시각을 분리한다. NPC 전원 탈출률을 올리는 것만으로 자연스러움이나 모델 정확도를 판정하지 않는다.

## 9. 우선순위와 남은 확인

설계상 우선순위는 **실제 출구 개구부·바닥/계단 → 단일 실외 통과 판정 → 문 조작과 통행 연결 → 전용 손/상체 모션 → 다인·되감기 검증**이다. 표시만 예쁘게 고쳐도 해결되지 않는 앞단 조건부터 다룬다. 먼저 대표 방문 1개와 중앙 출구 1개의 연속 흐름을 확인한 뒤 전체 문에 확대하는 편이 위험을 줄인다.

아직 확정하지 않은 사항:

- 실제 37개 방문과 계단실 문 각각의 미닫이/여닫이 형식, 경첩·손잡이·열림 방향, 실제 문 폭.
- 양끝 출구의 정확한 개구부와 외부 바닥 연결, 팀 모델링 담당이 수정할 메시 범위.
- 전용 문 애니메이션의 공급 및 RL/Manny별 적용 범위.
- 실외 분산 대기 구역과 건물 이탈/집결지 도착 중 보고할 지표.
- 기존 FDS 시나리오의 문 개폐·개구부 조건과 현재 게임 맵의 대응.

설계 방향 승인 후 구현 현황은 문서 상단의 진행 기록에서 관리한다. 설계 목표 전체를 완료한 것은 아니며, 양끝 개구부와 전용 손 모션은 확인/공급이 필요하다. 기존 사용자 파일과 작업 브랜치는 보존한다.
