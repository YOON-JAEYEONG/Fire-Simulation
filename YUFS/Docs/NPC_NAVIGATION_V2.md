# NPC 경로 탐색 v2 — 개인별 인지와 통행 조정

2026-09-08 구현, 2026-09-11 실행본 복원 및 화재 머티리얼 연결 반영. 현재 로컬·GitHub 브랜치는 모두 `JJW_NPC_BEHAVIOR`이다. NPC v2 소스는 `204a8d3`에 포함되어 있고, 이번 커밋은 그 위에 화재 연결과 복원 안내를 추가한다. `IT_YOON_JAEYEONG@4293ca3`은 구현의 출발 기준이며, `jjw/navigation-foundation`은 과거 로컬 작업 브랜치 이름이다.
프로젝트 위치와 실행 파일은 이전과 같다. `YUFS.uproject`를 열어 `Prototype` 맵을 에디터에서 재생한다.
이 문서가 현재 동작 설명이며, `NAVIGATION_HAZARDS.md`의 9월 8일 첫 구현 설명을 갱신한다.

## 눈으로 확인할 변화

- 경보가 울려도 전원이 같은 준비 시간을 거쳐 출발하지 않는다. 일부는 일찍 대피하고, 일부는 더 확인하며, 일부는 추가 단서를 기다린다.
- 연기와 고온 영역을 직접 감지하면 위험 인식이 높아진다. 짙은 연기에 직접 노출되거나 가까운 고온 값이 임계치를 넘으면 바로 대피한다.
- 앞·위·아래 방향의 관측과 가까운 열 감지 모두 벽과 바닥 충돌에 가려진다. 화면의 불꽃 픽셀을 인식하는 방식은 아니다.
- 가까이서 위험을 직접 감지한 NPC의 경고나, 보이는 주변 사람들의 대피가 다른 NPC에게 영향을 준다.
- 문으로 합류할 때 뒤의 NPC는 기다린다. 충돌할 두 NPC가 나란하거나 마주 보면 고정된 우선순위를 사용한다.
- 기다리는 위치가 통행을 막으면 뒤·대각선·옆의 공간을 검사해서 물러난다. 길과 바닥이 확인되지 않으면 그 위치로 이동하지 않는다.
- 경로 중간 모서리의 통과 허용 거리를 80cm에서 25cm로 줄여, 모서리를 지나치게 일찍 넘기는 문제를 줄였다.

## 인지·판단

`YUFSNPCPerceptionComponent`는 파일의 농도와 열 값을 읽는다. 온도는 내보낸 바이트를 255로 나눈 값이며 섭씨가 아니다.

- 시야 전방·상방·하방 및 머리 위를 최대 기본 40cm 간격으로 검사한다. 멀리 있는 단서는 가까운 단서보다 약하게 반영된다.
- 몸 가까이 180cm 범위의 열을 여러 방향에서 검사한다. 이것은 국소 데이터 기반 감지이며 물리적인 복사열 전달 모델은 아니다.
- 밀도·열이 있는 관찰 셀을 NPC별로 최대 8,192개 기록한다. 기본 30초 뒤 재관찰하지 않은 기억은 사라진다. 다시 확인한 셀이 맑으면 기존 위험 기록을 지운다.
- 경로 탐색은 개인의 관찰 기록과 전달받은 기록을 사용한다. 아직 확인하지 않은 셀은 추가 위험 비용이 0이며, 안전을 검증했다는 의미는 아니다.
- 비동기 탐색마다 기록을 고정해 다른 NPC나 이후 프레임의 변경과 섞이지 않게 한다.
- 위험을 직접 감지한 주변 NPC가 경고할 때 최대 256개 기록을 전달한다. 원래 관찰 시각을 유지해서 소문이 반복된다고 기억 수명이 계속 늘어나지 않는다.
- 사회적 인지에도 같은 층 높이와 벽 가림 검사를 적용한다. 현재 경고 전달은 동일 공간의 근거리 모델이며 음향 전파나 문 너머 대화 모델은 아니다.

`YUFSBehaviorStateMachine`의 개인 성향은 시작 위치와 `Personality Seed`로 한 번 정한다. 같은 실험 배치와 시드에서는 같은 성향이 나오며 공유 DataAsset을 수정하지 않는다.

| 설정 | 기본값 / 의미 |
| --- | --- |
| Early Alarm Response Fraction | 0.30. 경보만으로 비교적 일찍 결정하는 성향의 비율 |
| Verify Alarm Response Fraction | 0.45. 더 확인한 뒤 경보만으로도 결정하는 성향의 비율 |
| 나머지 성향 | 추가 감지·주변 대피·경고·안내를 기다림 |
| 일찍 반응하는 성향의 결정 시간 | 3~9초, 이후 개인별 준비 시간 |
| 더 확인하는 성향의 결정 시간 | 18~45초, 이후 개인별 준비 시간 |
| 위험 민감도 | 0.75~1.30배 |
| Heat Awareness Threshold | 0.20. 열 단서 인식 기준 |
| Emergency Heat Threshold | 0.65. 자기 위치 또는 가까운 열의 긴급 대피 기준 |
| Evidence Memory Seconds | 20초. 직접 감지했던 단서를 판단에 유지하는 시간 |
| 이동 속도 차이 | 기본 속도의 0.85~1.12배, 군중 감속과 기어가기 제한을 추가 적용 |

이 값들은 동작 비교를 위한 설계 초기값이며 실제 사람의 반응 비율이나 검증된 대피 시간 통계가 아니다. 구체적인 졸업 작품 실험 조건에 맞춰 조정해야 한다.

기존 `MaxMillingDuration`, `PerceivinDuration`은 에셋 호환성을 위해 남아 있지만 새 인지 모델의 출발 시간에는 사용하지 않는다. 개인별 확인 시간과 증거가 판단을 담당한다. `RiskAssessment` 열거형도 기존 기록 호환을 위해 유지한다.

기존 ONNX 입력 배열은 28개 그대로 유지했다. 새로운 열·경고·성향 값은 런타임 판단용이다. ONNX가 아직 대피를 결정하지 않은 NPC에게 이동을 지시하거나, 긴급 대피 상태에서 이동을 억제하는 경우 NPC 실행부가 상태에 맞게 제한한다. 새 모델을 학습하거나 가중치를 바꾼 것은 아니다.

## 통행과 막힘 복구

새 `YUFSLocalMovementComponent`가 목적지와 전체 경로를 유지하면서 국소 이동만 조정한다.

1. 기본 220cm 앞의 진행 방향을 비교해 충돌과 합류를 예상한다. 앞서 가는 NPC를 뒤쪽 NPC가 추월하며 밀지 않도록 기다린다.
2. 나란한 합류나 마주 오는 경우 액터 ID로 일관된 우선순위를 정한다. 우선순위는 관측 순서나 매번의 무작위 추첨에 따라 뒤집히지 않는다.
3. 먼저 기다리고, 가까이 막혀 있거나 대기가 길어지면 90/150/210cm 거리의 후방·대각선·측방 후보를 검사한다.
4. 후보는 NavMesh 투영, 같은 층 높이, 캡슐 전체 경로와 끝점 충돌, 연속 바닥 지지, 알고 있는 연기·열 위험을 모두 통과해야 한다.
5. 이동 입력으로 물러난 뒤 원래 목적지까지 다시 탐색한다. 순간이동이나 충돌 해제는 사용하지 않는다. 복구 중 RVO 속도 조정만 잠시 끄며 물리 충돌은 유지한다.
6. 기본 네 번의 복구 시도와 재시도 간격이 있다. 충분히 이동하거나 통행을 막던 대상의 위치·대상이 달라지면 시도 예산을 갱신한다. 안전한 공간이 없으면 `Blocked`로 남는다.

벽에 막혀 진행하지 못하는 경우도 복구 후보를 검사한다. `StartOffNavMesh`일 때는 가까운 동일 층의 NavMesh로 물리적으로 돌아갈 수 있는 후보를 검사한다. 벽 안에 깊이 박힌 초기 배치처럼 캡슐이 통과할 공간 자체가 없으면 복구할 수 없다.

군중을 따라가는 목적지는 이제 실제 주변 NPC의 목적지 하나다. 서로 다른 출구를 평균 내어 벽 안의 가상 목적지가 만들어지는 문제를 제거했다. 이미 같은 목적지로 이동 중이면 행동 이름이 바뀌더라도 경로를 불필요하게 다시 요청하지 않는다.

이것은 근거리 통행 조정이며 문 액터의 예약 시스템이나 건물 전체의 최적 군중 배분은 아니다. 대규모 NPC를 사용할 경우 현재 근거리 후보 탐색의 전체 액터 순회를 공간 인덱스로 바꾸는 최적화가 필요하다.

## 언리얼에서 비교하기

1. 실행 중인 에디터가 이전 DLL을 사용 중이면 종료하고 현재 폴더의 `YUFS.uproject`를 다시 연다. `Prototype`의 시작 버튼으로 실행한다.
2. NPC 디버그 표시의 `Cue`가 출발 판단 근거다: `Alarm`, `Smoke`, `Heat`, `PeerWarning`, `Crowd`, `Guidance`.
3. `Alarm trust`가 서로 다른지, 경보 이후 확인과 이동 시점이 나뉘는지 확인한다.
4. `Traffic`의 `Yielding`은 양보, `Recovering`은 물러나는 동작, `Blocked`는 복구 가능한 공간을 찾지 못한 상태다. `Yield to`로 기다리는 상대를 확인한다.
5. `Heat sight/near`와 `Known cells`로 실제 감지 여부를 확인한다. `Data: Ready`만으로 시각 효과와 데이터가 일치한다고 판단하면 안 된다.
6. 출력 로그에서 `[YUFS][Decision]`, `[YUFS][Traffic]`, `[YUFS][Nav]`, `[YUFS][Hazard]`를 검색하면 판단·통행·경로·데이터 진단을 볼 수 있다.

## 검증과 남은 문제

- Editor Development 빌드와 자동화 테스트 16개가 통과했다. 경보에 대한 개인차, 같은 시드의 재현성, 열·연기·경고·군중에 의한 판단, 행동 불능 유지, 모델 입력 폭, 벽 가림, 관찰 기억·만료·비동기 수명, 두 NPC의 양보와 해제, 벽·층간 이동·바닥 없는 복구 후보 거부를 포함한다. 앞선 경로 테스트 9개도 포함한다.
- 실제 맵 검증은 별도 기록에 보관한다. NullRHI에서는 테스트가 화재 프레임을 8fps로 지정하므로 정상 렌더링 재생 검증과 구분해야 한다.
- 최종 60초 맵 실행에서 20명 중 18명이 출구에 도달했다. 10초 시점에는 2명만 이동 중이었고, 늦게 출발한 NPC의 `Crowd` 판단과 `Yielding → Recovering → Following` 전환을 로그로 확인했다. 마지막 두 명은 계단 부근에서 이동 상태로 남았다. 전원 대피 성공을 확인한 검사는 아니다.
- 이 맵 실행에 기록된 경로의 연기·열 값은 모두 0이었다. 따라서 실제 맵 결과는 개인별 출발과 통행·복구 연결을 검증한 것이며, 화면의 화재를 정확히 감지·회피했다는 근거는 아니다. 열·연기 감지는 별도의 합성 데이터 및 실제 충돌 벽을 사용하는 자동화 테스트에서 확인했다.
- 맵 검증용 독립 저장 폴더에는 ONNX 모델이 없어 기존 규칙 기반 정책으로 실행했다. 일반 프로젝트의 모델 파일은 변경하지 않았다.
- **화면용 SVT와 BIN의 위치·시간·정규화 대응은 여전히 미확인이다.** `NAVIGATION_HAZARDS.md`에 확인한 해상도·프레임 차이와 팀원에게 필요한 정보를 기록했다. 임의로 두 데이터를 맞춰 놓지 않았다.
- NavMesh의 큰 다각형 안에서 위험을 세밀하게 우회하는 한계는 남는다. 위험한 최종 경로는 거부하며 프레임이 바뀐다는 이유만으로 동일한 실패 경로를 끝없이 즉시 다시 요청하지 않는다.
- 모든 문과 밀집 상황에서 막힘이 해소됐다고 보장하지 않는다. 깊은 초기 겹침, 충분히 넓지 않은 문, 잘못된 NavMesh와 충돌 설정은 맵에서도 확인해야 한다.
- 새 감지 및 교통 상태는 실시간 디버그·로그에 기록된다. 기존 타임라인 파일 형식과 CSV의 28개 학습 입력에는 추가하지 않았다.
- 사용자 에디터에서 연결한 화재 머티리얼 외부 액터 자산은 변경하지 않았다. main에 커밋하거나 원격에 푸시하지 않았다.
